# 제품 고유의 디자인 언어와 화면 문구 — 새 프로젝트 설계 / 기존 제품 보호

**적용 범위:** 처음 만드는 제품에서는 사용자의 목적과 콘텐츠를 근거로 독자적인 시각·언어 체계를 도출한다. **기존 제품에서는 사용자가 지정한 화면·요소만 변경**하며 색·배치·간격·문구를 개선 명목으로 무단 교체하지 않는다. 'AI 슬롭 방지'는 특정 색이나 감성을 일괄 금지하는 명령이 아니다.

이 문서는 화면을 멋있게 꾸미라는 문서가 아니라 **처음부터 무엇을 어떻게 표현할지 판단하는 절차**다. 사람의 행동 완결성·닫기 버튼의 도달 가능성·실제 데이터/상태 복원은 `UX_ACCEPTANCE.md`의 계약을 따른다. 같은 검증 규칙을 여기서 다시 늘리지 않는다.

## 1. 디자인 결정의 출발점

소스의 우선순위: **사용자가 제공한 취향·브랜드·참고 화면·명시적 요구 → 제품의 실제 목적과 핵심 콘텐츠·조작 → 플랫폼의 이해하기 쉬운 관례 → 프레임워크 기본값**.

- 이 제품의 가장 중요한 작업/콘텐츠는 무엇이고, 사용자가 처음·매번·오랫동안 쓰는 화면은 무엇인가?
- 실제 사용자가 무엇에 주의를 기울이고, 어떤 조작을 되풀이하고, 어디서 오류를 낼 수 있는가?
- 정보 밀도·편집 여부·대화·작업 흐름·기기 조건과 기존 브랜드 자산을 먼저 고려한다. 특정 제품 분야에 어울린다는 고정 색상·카드 구성 목록에서 골라 쓰지 않는다.
- 취향이 명시되지 않았다면 사용자를 끝없이 인터뷰하거나 여러 시안을 의무 생산하지 않는다. 설득력 있는 **한 가지 초기 방향**을 스스로 선택하고 실제 UI로 구현한다. 미확정 취향을 '사용자 승인'으로 기록하지 않는다.
- 아름다움만이 아니라 **목적에 따른 구분, 조작의 편안함, 일관된 표현, 자연스러운 문구**를 함께 선택한다.

## 2. 새 앱에서 구현 전에 정할 디자인 결정 6가지

`PRODUCT_BRIEF.md`의 제품 목표에 연결하여 실제 프로젝트에 필요한 내용만 `DESIGN_SYSTEM.md`에 간결히 채운다. 아래 문항은 **결정의 관점**이지 미리 만들어 둔 정답이나 강제 양식이 아니다. 모든 화면의 픽셀/색값/문구를 먼저 문서화하지 않는다.

| 결정 | 근거가 있어야 하는 판단 | 흔한 무의식적 기본값 |
|---|---|---|
| 전체적인 성격과 정보 밀도 | 차분함/명료함/활동성 등 제품 이용 맥락; 한 화면에 실제 필요한 정보량 | 앱이면 무조건 넓은 여백·카드·대형 헤더, 기능 수만큼 같은 메뉴 |
| 화면의 구조·시선 흐름 | 주요 콘텐츠/행동, 보조 정보, 취소/종료와 손의 이동; 탐색·편집·설정 역할 차이 | 기능 구현 순서를 그대로 쌓고 모든 화면에 같은 카드 스택 적용 |
| 글꼴과 위계 | 읽는 본문·편집 콘텐츠·숫자·제목·보조 정보의 비중, 한글 가독성 | 지나치게 큰 제목, 과한 볼드/영문 대문자, 격식 없는 임의 자간 |
| 색과 표면 | 사용자가 정한 브랜드 또는 제품 맥락; 강조/기본/위험/선택/상태의 의미 | 익숙한 초록·보라·파랑+연한 보조색을 근거 없이 재사용 |
| 버튼·아이콘·도형 | 자주 쓰는 작업의 중요도, 터치/키보드, 아이콘의 뜻·획 굵기·크기·라벨 일관성 | 전부 같은 둥근 버튼, 장식 아이콘 남용, 기본 Material 스타일 방치 |
| 화면 문구의 말투와 밀도 | 누가 어느 순간 어떤 정보를 얻는가, 서비스 성격과 자연스러운 언어 | 환영 인사/슬로건/격려/부제를 빈 공간 채우기 용도로 추가 |

**제품 고유성은 화려함이나 억지로 다른 색을 쓴다는 뜻이 아니다.** 평범한 컨트롤이 최선이라면 그것을 쓸 수 있다. 선택에 이유가 있고 사용 흐름과 잘 맞는지가 중요하다. 내부 일관성은 지키되 다른 앱의 익숙한 팔레트/템플릿을 복사해 동일하게 생기게 만들지 않는다.

## 3. 같은 디자인 시스템 ≠ 모든 화면을 같은 템플릿으로 만들기

공유할 것은 토큰(색·글자·간격), 아이콘의 획과 크기, 상호작용과 화면 전환 원칙이다. **그룹을 표현하는 형태까지 무조건 동일할 필요는 없다.** 콘텐츠가 중심인 화면에는 본문과 편집 영역, 탐색에는 목록과 간결한 메타 정보, 선택에는 쉽게 비교할 선택지, 관리에는 관계가 보이는 행/구분 등이 더 적합할 수 있다. 이는 **화면의 역할로 판단**하며 이 목록에서 앱 유형이나 UI를 강제로 고르지 않는다.

- 카드/패널은 독립된 정보 단위 또는 상호작용 집합일 때만 사용한다. 카드 없이 자연스럽게 구분되는 곳에는 텍스트·간격·구분선·면의 차이를 활용한다.
- 크기·굵기·여백·배치가 정보의 주/부 관계를 표현하게 한다. 전부 크게·진하게 만들거나 모든 기능을 같은 카드에 넣지 않는다.
- 색은 강조/상태/위험의 의미를 위해 아껴 쓸 수 있다. 모든 UI에 동일 브랜드색을 도배하지 않는다.
- 아이콘은 **하나의 스타일 언어**를 유지한다(예: 채움/윤곽, stroke, optical size, 꼭 필요한 레이블). 서로 다른 아이콘 팩과 이모지를 장식으로 섞지 않는다. 기본 라이브러리라도 의미를 구분할 수 있으면 사용한다.
- 실제 콘텐츠가 비어 있거나 길어도 화면이 성립하도록 한다. 긴 팝업의 닫기/확정은 본문 맨 아래까지 스크롤해야 찾는 구성으로 만들지 않는다. 상세 수용 기준은 `UX_ACCEPTANCE.md`.
- 불필요한 애니메이션으로 품질을 꾸미지 않는다. 재배치·모달·테마 전환·첫 프레임이 갑자기 튀거나 깜빡이는지도 살핀다.

## 4. CSS·Compose·기본 UI 라이브러리를 의식적으로 다루기

**플랫폼/프레임워크의 기본 모양은 제품 디자인 결정의 출발점일 수 있지만 자동으로 최종 정답이 되지는 않는다.** 기술 스택마다 '자주 나오는' 색과 둥근 형태를 검토한다.

- **Jetpack Compose / Material:** 기본 `lightColorScheme()` / `darkColorScheme()` 및 부분 지정된 `primary` 외 색상 역할, typography, shape, IconDefaults 등이 화면 전체를 사실상 결정하는지 확인한다. 브랜드에 맞는 의미색의 light/dark 조합과 컴포넌트 상태를 정의하되, Material 권장 사용성이나 기본 컨트롤을 무조건 버릴 필요는 없다. 다크모드에서 의도치 않은 기본 보라/자주색이 남는지 확인한다.
- **Web / WebView:** 익숙한 CSS `--green`, `--pale`, 둥근 카드·칩·그림자 세트를 이전 앱처럼 무근거 복사하지 않는다. CSS 변수와 컴포넌트를 사용할 땐 이 제품의 콘텐츠·톤·정보 구조에 맞춰 설계하고 라이트/다크·상태 스타일을 연동한다.
- **다른 스택 / 플랫폼:** 라이브러리의 샘플 화면·테마 색·아이콘 팩을 그대로 적용한 결과가 아닌지 검토한다. 플랫폼의 접근성·조작 관례는 존중한다. 기술 스택을 바꾸거나 새 디자인 시스템 라이브러리를 도입하는 것은 현재 작업에 필요한 경우에만.
- 반대로 초록·보라·파랑 자체를 금지하거나 새 앱마다 기괴한 색을 뽑아 차별화하지 않는다. 사용자가 명시한 기존 색과 브랜드 자산은 유지한다.

## 5. 화면 문구는 디자인과 함께 결정한다

문구는 완성된 화면에 나중에 장식처럼 얹는 것이 아니라 **화면의 정보 위계와 같은 단계에서 설계**한다. 타이틀·부제·버튼·플레이스홀더·빈 상태·에러 문구가 서로 어떤 정보를 전달하는지 살핀다.

1. **필요성:** 없애도 상태·선택·결과·다음 행동에 대한 이해가 같다면 우선 제거하거나 다른 요소와 합친다. 빈 공간을 채우는 설명과 기능 목록의 문장 재진술을 만들지 않는다.
2. **맥락:** 해당 제품의 바로 이 순간과 연결되는 말인가? 다른 앱·다른 상태에 그대로 옮겨도 어울리는 추상 표어라면 다시 쓴다.
3. **기능:** 버튼 레이블은 실제 결과를 예측 가능하게 한다. 중요한 삭제·외부 전송·데이터 손실에는 정확한 결과와 복구 가능성을 설명한다. 로딩·실패는 무엇이 유지되었고 어떻게 다시 할 수 있는지 알린다.
4. **어조:** 한국어라면 자연스럽고 실제 사용자가 쓸 만한 표현을 우선한다. UX 맥락이 없다면 영어 표어·형식적인 다정함·과장된 약속·중복 인사·수치 재진술을 추가하지 않는다. 브랜드에 맞는 어조는 사용자가 제공한 기준을 따른다.
5. **감정:** 감성 문구를 전부 금지하지 않는다. 때와 행동에 맞는 짧은 표현이 경험을 좋게 만든다면 사용할 수 있다. 다만 매번 진입하는 화면의 반복 문구는 피로를 줄 수 있으므로 신중히 배치한다.
6. **중복:** 상단 제목이 설명한 작업을 부제·플레이스홀더·버튼 위 설명이 연달아 반복하지 않는지 확인한다. 같은 통계 수치를 그래프/본문/배지에서 의미 없이 세 번 설명하지 않는다.

**자가 질문:** '이 문장은 사용자가 **지금** 무엇을 알아야 하기에 있는가?' '없애면 의미가 사라지는가?' '기계적으로 친절하게 보이려고 덧붙인 말인가?'  어색하면 없애거나 짧고 구체적으로 고친다. 다만 중요한 정보까지 지워서 차갑고 불친절한 UI로 만들지 않는다.

## 6. 실제 구현용 의미 기반 토큰

새 앱에서 실제 기술 스택에 맞게 **한 곳**에 정의한다. 사용자에게 모든 값을 일일이 고르라고 요청하지 않는다. 이 표의 이름은 예시 역할이며 그대로 복사해야 하는 API가 아니다.

| 영역 | 처음부터 연결할 의미 |
|---|---|
| 색 | `background`, `surface`, `onSurface`, `muted`, `primary`, `onPrimary`, `border`, `selected`, `focus`, `error`, `warning`, `disabled` (라이트/다크) |
| 글꼴 | 화면 제목, 섹션 제목, 본문, 보조 정보, 수치, 입력과 도움말의 크기·행간·굵기 |
| 간격과 형태 | 콘텐츠 주변 여백, 그룹 관계, 클릭 면적, 모서리 반경, 필요할 때만 고도/그림자 |
| 아이콘 | 크기, stroke/fill, 시각적 무게, 필요한 레이블과 의미 일치 |
| 상태 | default, pressed, selected, focused, disabled, loading, empty, error, success |
| 기기 | safe area, 키보드/IME, 폴더블·작은 창, 글꼴 확대, reduced motion |

상태에 따라 의미색이 실제로 적용되는지 확인한다. 숫자나 보조 라벨의 명암도 읽을 수 있어야 한다. 화면의 형태가 바뀌어도 조작·저장·복귀가 정상이어야 한다.

## 7. 새 화면의 최소 설계·검증 흐름

**초기 개발 또는 명시적으로 승인된 UI 개편일 때:**

1. `PRODUCT_BRIEF.md`에서 핵심 이용 상황·콘텐츠·기존 승인 조건을 확인한다.
2. 위 6가지 관점으로 **제품 고유의 일관된 한 방향**을 정한다. 근거가 명백하면 사용자를 다시 질문하지 않고 결정한다. `PRODUCT_BRIEF.md`에는 핵심 결정을 짧게 기록한다.
3. 코드에 실제 화면을 구현하며 **화면별 역할에 맞는 레이아웃과 문구**를 적용한다. 별도 이미지 시안/가짜 HTML 프로토타입/대안 여러 개를 의무적으로 만들지 않는다.
4. 가능할 때 실제 앱의 대표 화면을 보고 이 세 가지를 분리해 점검한다.
   - **템플릿 관성:** 색/카드/버튼/아이콘을 이유 없이 기본 라이브러리나 과거 앱에서 가져오지 않았는가? 화면마다 같은 카드 스택을 반복했는가?
   - **문구 관성:** 불필요한 부제·슬로건·격려·동일 정보 중복·자연스럽지 않은 표현이 있는가? 반대로 중요한 안내를 없애지 않았는가?
   - **실제 사용감:** 콘텐츠와 조작이 가려지지 않고, 좁은 화면·큰 글꼴·키보드·다크모드·실제 데이터에서도 동작하는가?
5. 수정할 필요가 있는 **실제 문제**만 보완하고 가능한 사용자 흐름을 표적 검증한다. 디자인을 숫자로 점수화해서 사용자의 미적 판단을 대체하지 않는다.

**작은 버그·국소 UI 변경일 때:** 기존 스타일을 그대로 활용하고 해당 화면/행동만 확인한다. 새 브랜드 방향이나 디자인 라이브러리·추가 대형 문서를 강제로 도입하지 않는다.

## 8. 변경 권한과 완료 보고

새 제품의 초깃값은 사용자 설명으로부터 결정된 **초안**이며 나중에 사용자가 다른 방향을 요청할 수 있다. 기존 앱에서 승인된 시각적 정체성·문구·레이아웃은 보존 대상이다. 디자인 스킬이나 스타일 가이드가 기존 승인 조건보다 우선하지 않는다.

최종에는 실제 수정한 화면, 주요 디자인 판단과 이유, 실제 렌더링/기능 확인 범위만 간결히 보고한다. 테스트 통과와 디자인의 인간적 만족도를 같은 것으로 주장하지 않는다.

## 배민 블랙 전용 디자인 적용

- **핵심 경험:** 배민 원본 화면을 방해하지 않으면서 가게별 개인 기록을 바로 확인하는 조용한 보조 UI.
- **목록 배지:** 작은 빨강 계열 금지 아이콘. 터치 불가, 스크롤 중 숨김, 180ms 정지 후 새로운 노드 좌표에 표시. 기존 카드의 실제 버튼과 가게명을 가리지 않는다.
- **상세 경고:** 현재 가게 식별이 확실할 때에만 작고 간결하게 노출. 목록 배지와는 별도 생명주기.
- **관리 화면:** 가게 검색 → 상태 필터 → 결과 목록 → 메모 기록으로 시선 이동 최소화. 긴 메모/키보드 상황에서 저장·취소 접근성 보장.
- **문구:** 사용자 자신의 기록임을 명확히 한다. 배민의 공식 가게 평가나 서비스 제재처럼 오해하게 만들지 않는다.
- **검증:** 작은 화면/확대 글씨/다크 모드/가로 회전과 스크롤·앱 이탈·복귀 시 보이는 상태를 점검.

제품의 확정 기능·UI 배지 동작은 `docs/PRODUCT_BRIEF.md`와 `docs/DECISIONS.md`를 따른다. 디자인 품질 절차를 핑계로 이를 다시 분석하거나 바꾸지 않는다.


### 1.0 구현 토큰과 구조
차분한 개인 기록 도구로, 따뜻한 회백색/차콜 표면과 붉은 블랙리스트 의미색을 사용한다. 주의는 황갈색, 나머지는 중립색이며 라이트·다크 토큰을 `ui/Theme.kt`에 모았다. 메인은 검색과 필터 뒤에 밀도 있는 가게 행을 두고, 기록은 날짜와 본문 중심으로 읽는다. 편집은 전체 화면과 고정 상단 저장/취소를 사용하며 IME 영역을 피한다. 설정은 짧은 설명과 직접 조작을 묶는다. 배지는 22dp 금지 마크로 이름 오른쪽의 확보된 공간에만 놓는다.
