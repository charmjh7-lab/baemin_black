# Visual quality: design decisions before slop cleanup

이 스킬의 단일 상세 기준은 `docs/DESIGN_SYSTEM.md`다. 이 파일에 중복된 긴 규칙을 다시 작성하지 않는다. UI 품질은 '나중에 슬롭을 삭제하기'보다 **처음부터 화면과 문구를 결정하는 과정**에서 확보한다.

1. `PRODUCT_BRIEF.md`와 현재 실제 화면/승인된 디자인을 먼저 읽는다. 처음 만드는 화면인지, 일부만 바꾸도록 요청된 기존 화면인지 구분한다.
2. 신규/승인 개편이면 제품의 콘텐츠·사용자·목적에 맞는 시각적 방향을 정한다: **위계·밀도, 배치, 타이포그래피, 의미 색, 컴포넌트/아이콘 언어, 마이크로카피의 톤**. 앱 분류표나 이전 프로젝트 색상·화면 틀을 재사용하지 않는다. 한 방향을 선정하고 구현한다.
3. Compose `MaterialTheme`의 미지정 light/dark 역할, WebView/CSS의 익숙한 파스텔+초록 버튼/둥근 카드 조합, 라이브러리의 데모 아이콘이 무의식적 기본값이 되었는지 확인한다. **특정 색 금지가 아니라 선택 근거를 검토**한다.
4. 모든 화면을 같은 카드 템플릿으로 만들지 않는다. **공통 디자인 토큰의 일관성**과 **화면 역할에 맞는 서로 다른 구성**을 양립시킨다. 문구도 제목·보조·버튼·피드백이 반복 없이 함께 정보를 전달해야 한다.
5. 각 문장이 존재할 이유를 심사한다. 상투적 인사·장식 문구·추상 표어·불필요한 설명을 정리하되, 사용자의 이해에 필요한 문장과 상황에 맞는 감성 표현까지 기계적으로 지우지 않는다.
6. 대표 실제 화면에서 정보·정렬·간격·명암·아이콘·문구와 사용성(작은 화면/키보드/다크/닫기 접근성)을 확인한다. 시안 이미지·정적 스크린샷만으로 앱 동작이 완료되었다고 주장하지 않는다.

기존 앱의 사소한 수정에서는 디자인 탐색과 전체 재검토를 하지 않는다. 사용자가 승인하지 않은 변경은 적용하지 않고 별도 제안으로만 남긴다. 유관한 `interaction-completeness`와 `risk-based-verification`은 작업에 해당할 때만 호출한다.
